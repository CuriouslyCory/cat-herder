# Plan: Issue #13 — Admin Role Foundation (users.isAdmin + adminProcedure)

## Summary & goal

Introduce a first-class admin concept end-to-end: a `users` table keyed on WorkOS user ID
with an `isAdmin` boolean, bootstrap logic seeded from `ADMIN_BOOTSTRAP_EMAILS`, an
`adminProcedure` tRPC middleware that enforces admin-only access, and `isAdmin` surfaced
server-side in the play page so the client game object has it without an extra client
round-trip.

The DB driver is `neon-http` (drizzle-orm/neon-http + @neondatabase/serverless), which
means **no interactive transactions** and no `db.transaction()` calls — all writes must use
single-statement Drizzle helpers such as `.onConflictDoNothing()` and `.onConflictDoUpdate()`.

## ADR draft: docs/adr/0001-admin-role-model.md

```markdown
# ADR 0001 — Admin Role Model

**Status:** Accepted  
**Date:** 2026-06-29  
**Issue:** #13

## Context

The cat-herder game is adding map-authoring features that must be gated behind an admin
check. WorkOS (the auth provider) handles authentication; it does not own the authorisation
data for this application. We need a decision on where and how to store who is an admin.

Constraints:
- DB driver is neon-http (no interactive transactions).
- WorkOS user IDs (`user_01XXXXXXXX`) are the canonical identity key already used in
  `characters`, `gameSaves`, and `debugOverrides` tables.
- The project uses Drizzle ORM with pgTableCreator prefix `cat-herder_`.
- First-admin bootstrap must happen at row creation time only (so manual demotions persist).

## Decision

Add a `users` table with columns `userId` (PK, WorkOS user ID varchar 256), `email` (varchar
256, not null), and `isAdmin` (boolean, not null, default false). Upsert a row on the first
authenticated server touch (the play page `withAuth` call). Check `ADMIN_BOOTSTRAP_EMAILS`
(comma-separated) only when inserting a new row; use `.onConflictDoNothing()` on the upsert
so subsequent logins never flip the bit.

An `adminProcedure` extends `protectedProcedure` with a middleware that queries `users.isAdmin`
for the authenticated user, throws `FORBIDDEN` if false/absent, and passes through if true.

## Consequences

Positive:
- Simple, auditable: one column, one table, visible in `db:studio`.
- Bootstrappable via env var; fallback is a direct `db:studio` flip (documented).
- No extra client round-trip: `isAdmin` is fetched in the `PlayPage` server component
  alongside `withAuth` and threaded into the `GameUser` prop.
- Minimal schema surface — easy to extend to a full roles table later.

Negative:
- Boolean does not support multiple role tiers (e.g., moderator). Migration to a roles
  table would require a new column or a separate relation.
- Admin list in env var is only a convenience bootstrap, not a runtime source of truth.

## Alternatives considered

### A. `isAdmin` boolean on `users` table (chosen)
As described above. Lowest complexity, sufficient for current scope.

### B. Roles table (`users_roles` with role enum)
Supports multi-tier roles (admin, moderator, etc.). Overhead is high for a feature that
currently needs only a binary flag. Can be migrated to later if needed.

### C. WorkOS Organizations roles
WorkOS supports role assignments in Organizations. This would avoid a custom `users` table
for auth metadata, but couples the app's authorization model to WorkOS semantics, makes
local testing harder (real WorkOS org required), and adds latency (WorkOS API call per
check vs. local DB row).

### D. `isAdmin` on the existing per-user tables (characters/gameSaves)
Avoids a new table but mixes auth concerns with game data. Rejected: wrong abstraction layer.
```

## Files to modify

### 1. `src/server/db/schema.ts`

Add the `users` table after the existing imports, following the `createTable` convention
already established:

```ts
export const users = createTable("user", (d) => ({
  userId: d.varchar({ length: 256 }).primaryKey(),   // WorkOS user.id
  email:  d.varchar({ length: 256 }).notNull(),
  isAdmin: d.boolean().notNull().default(false),
  createdAt: d
    .timestamp({ withTimezone: true })
    .default(sql`CURRENT_TIMESTAMP`)
    .notNull(),
  updatedAt: d
    .timestamp({ withTimezone: true })
    .$onUpdate(() => new Date()),
}));
```

No extra indexes needed initially — `userId` is the PK and the only query key.

### 2. `src/env.js`

Add `ADMIN_BOOTSTRAP_EMAILS` to the `server` block and the `runtimeEnv` map:

// in runtimeEnv:

### 3. `src/server/game/upsertUser.ts` (new file)

```ts
import { env } from "~/env";
import { users } from "~/server/db/schema";
import type { db as DbType } from "~/server/db";

export async function upsertUser(
  db: typeof DbType,
  userId: string,
  email: string,
): Promise<{ isAdmin: boolean }> {
  const bootstrapEmails = (env.ADMIN_BOOTSTRAP_EMAILS ?? "")
    .split(",")
    .map((e) => e.trim().toLowerCase())
    .filter(Boolean);

  const isAdminByBootstrap = bootstrapEmails.includes(email.toLowerCase());

  // Insert with bootstrap flag; if the row already exists, do nothing (preserve existing isAdmin).
  await db
    .insert(users)
    .values({ userId, email, isAdmin: isAdminByBootstrap })
    .onConflictDoNothing();

  // Re-read the row to return the actual stored value (handles both insert and conflict paths).
  const row = await db.query.users.findFirst({
    where: (u, { eq }) => eq(u.userId, userId),
  });

  return { isAdmin: row?.isAdmin ?? false };
}
```

Key design decisions:
- `.onConflictDoNothing()` means a second login never touches `isAdmin`. Only the first
  insert respects `ADMIN_BOOTSTRAP_EMAILS`.
- The follow-up `findFirst` is safe with neon-http (no transaction needed — the row either
  was just inserted or was already there; either way `findFirst` reads the correct state).
- `email` is updated on conflict **only if you need it**. Because we use
  `.onConflictDoNothing()`, email changes in WorkOS will NOT be reflected. If email sync
  is required later, switch to `.onConflictDoUpdate({ target: users.userId, set: { email } })`.
  This is a known trade-off; document it in the file.

### 4. `src/server/api/trpc.ts`

Add `adminProcedure` after `protectedProcedure`. Import `users` from the schema and `eq`
from drizzle-orm:

```ts
import { eq } from "drizzle-orm";
import { users } from "~/server/db/schema";

// ... existing code ...

/**
 * Admin-only procedure.
 *
 * Extends protectedProcedure: throws UNAUTHORIZED if unauthenticated (inherited),
 * throws FORBIDDEN if the authenticated user does not have isAdmin = true.
 */
export const adminProcedure = protectedProcedure.use(async ({ ctx, next }) => {
  const row = await ctx.db.query.users.findFirst({
    where: eq(users.userId, ctx.user.id),
  });

  if (!row?.isAdmin) {
    throw new TRPCError({ code: "FORBIDDEN" });
  }

  return next({ ctx });
});
```

Note: `protectedProcedure` already narrows `ctx.user` to non-null, so `ctx.user.id` is
safe here. `adminProcedure` inherits that narrowing.

### 5. `src/app/play/page.tsx`

Thread `isAdmin` into `safeUser`. The `upsertUser` helper is called here on every play page
load — this is the "first authenticated server touch" that creates the row.

```ts
import { withAuth } from "@workos-inc/authkit-nextjs";
import { db } from "~/server/db";
import { upsertUser } from "~/server/game/upsertUser";
import { GameLoader } from "./_components/GameLoader";

export default async function PlayPage() {
  const { user } = await withAuth({ ensureSignedIn: true });

  // Upsert the user row (creates on first visit, no-op on conflict).
  // This is where the bootstrap flag is applied if this is the first login.
  const { isAdmin } = await upsertUser(db, user.id, user.email ?? "");

  const safeUser = {
    id: user.id,
    firstName: user.firstName,
    email: user.email,
    isAdmin,
  };

  return (
    <main style={{ width: "100vw", height: "100vh", overflow: "hidden" }}>
      <GameLoader user={safeUser} />
    </main>
  );
}
```

`user.email` from WorkOS is typed as `string | null`. Pass `user.email ?? ""` to
`upsertUser` (an empty string is a no-op for the bootstrap check since it won't match any
email in the list).

## ⚠️ ORCHESTRATOR OVERRIDE (supersedes the migration section below)

Investigation found: **no `drizzle/` migrations dir or `_journal.json` exists anywhere** in the repo, and the 4 existing tables (`post`, `character`, `game_save`, `debug_override`) are present in the live `neondb`. The project's established workflow is **`pnpm db:push`** (push schema directly), NOT `db:generate`/`db:migrate`. Running `db:generate` now would emit CREATE TABLE for all existing tables (no baseline snapshot) and `db:migrate` would then fail.

Therefore:
- The implementation agent **must NOT** run `db:generate`, `db:migrate`, or `db:push`, and must NOT create a `drizzle/` directory or any `.sql` file. Just edit `src/server/db/schema.ts` to add the `users` table.
- Schema application to the live dev DB is done via `pnpm db:push` **by the orchestrator** (additive, non-destructive) after gate review.
- The ADR must record the migration mechanism: "schema applied via `db:push` per project convention; no migrations dir exists." Acceptance criterion "migration generated and applied" is satisfied by the additive `db:push`.
- The four gates (`pnpm test/lint/typecheck/build`) do not require the table to exist (tests mock the db; build/typecheck don't connect), so they pass regardless.

## DB migration procedure (SUPERSEDED — see override above; do not run these)

1. Ensure `DATABASE_URL_UNPOOLED` (direct connection) is set in `.env`.
2. Run `pnpm db:generate` from the repo root. Drizzle-kit reads `drizzle.config.ts`
   (schema at `./src/server/db/schema.ts`, output dialect `postgresql`) and generates a
   `.sql` migration file under `./drizzle/` (the default output directory — confirm after
   first run that drizzle.config.ts has no explicit `out:` key; it currently has none).
3. Inspect the generated file to confirm it contains:
   - `CREATE TABLE "cat-herder_user" (...)` with the correct columns.
   - No `DROP` statements on existing tables.
4. Run `pnpm db:migrate` to apply the migration to the live Neon database. This requires a
   real Neon connection and **cannot run in CI without one**.

**Migration application requires a live Neon DB.** CI/CD pipelines that do not have
`DATABASE_URL_UNPOOLED` configured cannot run `db:migrate`. The migration file is committed
to the repo; a human (or a CI step with DB credentials) applies it before or after deploy.

`pnpm build` and `pnpm typecheck` do NOT require a DB connection — they use
`SKIP_ENV_VALIDATION=true` or a mock `.env` in CI to bypass `@t3-oss/env-nextjs`
validation.

**Test cases to cover:**

1. **Unauthenticated → UNAUTHORIZED**
   - Build ctx with `user: null`.
   - Call any `adminProcedure` endpoint.
   - Expect tRPC error code `UNAUTHORIZED`.
   - `mockFindFirst` must NOT be called (auth check is first).

2. **Authenticated non-admin → FORBIDDEN**
   - Build ctx with `user: { id: "user_123" }`.
   - `mockFindFirst.mockResolvedValueOnce({ isAdmin: false })`.
   - Expect tRPC error code `FORBIDDEN`.

3. **Authenticated, no user row → FORBIDDEN**
   - Build ctx with `user: { id: "user_orphan" }`.
   - `mockFindFirst.mockResolvedValueOnce(undefined)`.
   - Expect tRPC error code `FORBIDDEN`.

4. **Authenticated admin → passes through**
   - Build ctx with `user: { id: "user_admin" }`.
   - `mockFindFirst.mockResolvedValueOnce({ isAdmin: true })`.
   - Procedure completes successfully.

5. **upsertUser bootstrap: first insert sets isAdmin for bootstrap email**
   - Import `upsertUser` directly.
   - Mock `db.insert().values().onConflictDoNothing()` to resolve.
   - Mock `db.query.users.findFirst` to return `{ isAdmin: true }`.
   - Assert `upsertUser(db, "user_1", "admin@example.com")` returns `{ isAdmin: true }`.

6. **upsertUser bootstrap: second insert (conflict) does not flip isAdmin**
   - Same test but `findFirst` returns `{ isAdmin: false }` (simulating a previously
     demoted admin). Assert result is `{ isAdmin: false }`.

7. **upsertUser: non-bootstrap email gets isAdmin: false**
   - Call with `"notadmin@example.com"`, findFirst returns `{ isAdmin: false }`.
   - Assert `{ isAdmin: false }`.

**Note:** The `users.findFirst` in `adminProcedure` uses `ctx.db.query.users.findFirst`.
The mock must wire up `db.query.users.findFirst` at the module level, just as beacon-save

Vitest environment is `node` (confirmed in `vitest.config.ts`). No Three.js / DOM involved.

## Review step

A reviewer must confirm the following before merging:

1. **Bootstrap consulted only at creation:** `upsertUser` uses `.onConflictDoNothing()`,
   NOT `.onConflictDoUpdate()` for the `isAdmin` column. The bootstrap email list is only
   applied to the `values()` call — a row that already exists keeps its stored `isAdmin`.

2. **FORBIDDEN vs UNAUTHORIZED correct:** `adminProcedure` inherits `protectedProcedure`'s
   UNAUTHORIZED throw (unauthenticated case). The admin check only runs after auth is
   confirmed and throws FORBIDDEN. Never mix the two error codes.

3. **No client round-trip for isAdmin:** `isAdmin` is fetched inside the `PlayPage` server
   component (RSC, runs on server), passed as a prop via `safeUser` to `GameLoader`, then
   into `GameCanvas` → `Game`. No tRPC query from the client is made to obtain `isAdmin`.

4. **Env var declared and documented:** `ADMIN_BOOTSTRAP_EMAILS` appears in `src/env.js`
   (server block + runtimeEnv) and `.env.example` with a comment explaining it is only
   consulted at row creation and that `db:studio` is the fallback promotion path.

5. **Migration file committed:** The `drizzle/<timestamp>_users_table.sql` file is included
   in the PR so reviewers can audit the DDL.

6. **GameUser type updated:** `isAdmin: boolean` added to the interface — no `| undefined`
   or optional — so downstream consumers get a strict type.
