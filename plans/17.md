# Plan: Issue #17 — Editor DB Persistence UI

## Summary & goal

Replace the MapEditor's browser-JSON file save/load (download/upload) with database-backed map management wired through the existing `GameTrpcAdapter` injection pattern. The editor panel gains Save (name + DB persist, remembering map id across saves), Load (pick from DB list), Set-as-Default, and Delete (client-side + server-enforced guard). Server errors including FORBIDDEN are surfaced inline. The editor remains dev-only/tree-shaken, and all DB writes stay admin-enforced by the `adminProcedure` wrapper on the server.

---

## Backend-adapter extension

### Current `GameTrpcAdapter` interface (src/game/engine/Game.ts, lines 73–80)

```ts
export interface GameTrpcAdapter {
  upsertSave(input: { version: string; saveData: SaveData }): Promise<void>;
  getSave(): Promise<{ version: string; saveData: Record<string, unknown> } | null>;
  deleteSave(): Promise<void>;
}
```

### New additions to `GameTrpcAdapter`

Extend the interface with five map operations that mirror `src/server/api/routers/map.ts` exactly:

```ts
export interface GameTrpcAdapter {
  // ... existing game save operations ...

  // Map operations (admin-only server-side; present even for non-admins
  // so the type is uniform; non-admin calls will receive FORBIDDEN from server)
  mapList(): Promise<Array<{ id: number; name: string; isDefault: boolean; createdAt: Date }>>;
  mapGet(input: { id: number }): Promise<{ id: number; name: string; mapData: unknown; isDefault: boolean }>;
  mapSave(input: { id?: number; name: string; mapData: MapData }): Promise<{ id: number; name: string }>;
  mapSetDefault(input: { id: number }): Promise<void>;
  mapDelete(input: { id: number }): Promise<void>;
}
```

### Mapping to tRPC procedures

| Adapter method     | tRPC procedure        | Auth         |
|--------------------|-----------------------|--------------|
| `mapList()`        | `api.map.list`        | adminProcedure |
| `mapGet({ id })`   | `api.map.get`         | adminProcedure |
| `mapSave({ ... })` | `api.map.save`        | adminProcedure |
| `mapSetDefault`    | `api.map.setDefault`  | adminProcedure |
| `mapDelete({ id })` | `api.map.delete`     | adminProcedure |

### Wiring from GameCanvas → Game → MapEditor (mirroring the existing pattern)

**The existing pattern** (src/app/play/_components/GameCanvas.tsx, lines 54–87):

1. `GameCanvas` calls `api.game.*.useMutation()` and `api.game.getSave.useQuery()` inside the React component.
2. It stores refs to the latest mutation functions via `useRef` + `useEffect`, updated on every render (lines 65–72).
3. A `useMemo` builds a stable `GameTrpcAdapter` object that delegates through those refs (lines 75–87).
4. This adapter is passed as `trpc` to `new Game(canvas, { user, character, trpc: trpcAdapter, initialMap })` (line 164).
5. `Game` passes it to `new Persistence(gameState, opts.trpc, eventBus)` (line 289), and now must also pass it to `MapEditor`.

**Extension for map operations:**

- In `GameCanvas`, add `useMutation` calls for `api.map.list`, `api.map.get`, `api.map.save`, `api.map.setDefault`, `api.map.delete`. Mirror the ref pattern exactly.
- Add the five methods to the `trpcAdapter` `useMemo`.
- In `Game.ts` constructor (line 344), change the `MapEditor` construction to pass `opts.trpc` alongside the existing arguments:

```ts
// Before (line 344-352):
this.mapEditor = new MapEditor(
  canvas,
  this.cameraController,
  { pause: () => this.pause(), resume: () => this.resume() },
  this.sceneManager,
  this.mapManager,
);

// After:
this.mapEditor = new MapEditor(
  canvas,
  this.cameraController,
  { pause: () => this.pause(), resume: () => this.resume() },
  this.sceneManager,
  this.mapManager,
  opts.trpc,          // <-- new
  opts.user,          // <-- new (for isAdmin check)
);
```

**Why injected callbacks, not a vanilla tRPC client:**

The existing codebase deliberately keeps the game engine decoupled from `~/trpc/*`. `Persistence` already receives a `GameTrpcAdapter` from GameCanvas and never imports tRPC directly. A vanilla `createTRPCProxyClient` inside the editor would re-import `~/trpc/react.tsx` (React-only) or require duplicating the HTTP link configuration — both break the dev-only tree-shaking guarantee (the import chain would carry tRPC into the editor bundle path). The injected-callback approach is zero new infrastructure: extend the existing `GameTrpcAdapter` interface, extend the existing `useMemo` in `GameCanvas`, and pass `opts.trpc` to `MapEditor`. The React hook layer (auth cookies, React Query cache) stays in React where it belongs.

## Editor UI changes

### What to remove

In `_buildPanel()` (src/game/maps/MapEditor.ts, lines 1131–1194):

- The entire "File" section (lines 1131–1194): `fileSep`, `fileTitle`, `saveBtn` with `saveMap()` listener, `fileInput`, `loadBtn` with `fileInput.click()` listener.
- The `_fileInput` private field (line 277) and its null-clear in `dispose()` (line 959).
- The `saveMap()` public method (lines 462–476) and `loadFromFile()` public method (lines 479–494) — these become dead code once the panel is replaced.

### What to add

Replace the removed "File" section with a new "Database" section in `_buildPanel()`. All DB operations are async; use `_showError()` for failures and a transient status message for success.

**New private fields to add:**

```ts
private _currentMapId: number | null = null;   // remembers id after first save/load
private _currentMapName: string = "untitled";  // pre-fills Save name input
private _mapNameInput: HTMLInputElement | null = null;
private _mapListSelect: HTMLSelectElement | null = null;
private _setDefaultBtn: HTMLButtonElement | null = null;
private _deleteBtn: HTMLButtonElement | null = null;
private _statusDisplay: HTMLElement | null = null;  // transient success/info messages
```

**Save button behavior:**

1. Reads name from `_mapNameInput` (defaults to `_currentMapName`).
2. Calls `this._trpcAdapter.mapSave({ id: this._currentMapId ?? undefined, name, mapData: this.getMapData() })`.
3. On success: stores returned `id` in `_currentMapId`, updates `_currentMapName`, shows status "Saved".
4. On error: calls `_showError(err.message)`.
5. While saving: disable the button; re-enable on completion.

**Load flow:**

1. "Refresh List" button calls `mapList()` and populates `_mapListSelect` with `{ id, name, isDefault }` entries.
2. "Load Selected" button reads the selected id, calls `mapGet({ id })`, validates with `mapDataSchema.safeParse()`, then calls `this.loadMapData(result.data)` and sets `_currentMapId` and `_currentMapName`.

**Set-as-Default button:**

- Enabled only when `_currentMapId !== null`.
- Calls `mapSetDefault({ id: _currentMapId })`.
- On success: refreshes the list to reflect the new default.
- On error: surfaces error inline.

**Delete button:**

- Enabled only when `_currentMapId !== null`.
- **Client-side guard** (mirrors server guard in map.ts lines 169–185): disable the button if the currently loaded map appears as `isDefault: true` in the list, or if the list has only one entry.
- On click: confirm prompt (`window.confirm`) then call `mapDelete({ id: _currentMapId })`.
- On success: clears `_currentMapId`, refreshes list.
- On error (FORBIDDEN or NOT_FOUND): surface inline.

**Admin check:**

The `MapEditor` constructor receives `user: GameUser` (which has `isAdmin: boolean` from `src/game/engine/Game.ts` line 59). If `!user.isAdmin`, the entire DB section is rendered as disabled (all buttons `disabled`, with a label "Admin only"). Calls that reach the server still get FORBIDDEN — this is UI convenience, not a security boundary.

**Error / status display:**

- `_errorDisplay` (already exists, line 279) shows errors in red.
- Add `_statusDisplay` (new) shows transient success messages in green, auto-clears after 3 seconds.
- `_showError(null)` clears error; `_showStatus(msg)` sets success.

**Keep dev-only / tree-shaken:**

The existing guard is at `MapEditor` constructor line 293:
```ts
if (process.env.NODE_ENV === "production") return;
```
This must not change. In production `_buildPanel()` is never called, so all DOM construction (including new DB section) is unreachable and tree-shaken by Next.js. The `GameTrpcAdapter` interface extension adds no runtime code — it is pure TypeScript types erased at compile time. The guard in `Game.ts` (line 344) also remains unchanged:
```ts
if (process.env.NODE_ENV !== "production") {
  this.mapEditor = new MapEditor(...);
}
```

## Risks and unknowns

1. **Calling tRPC from non-React code**: The editor is a plain TypeScript class. The chosen solution (injected callbacks from `GameCanvas`) avoids importing `~/trpc/react.tsx` from within the editor, which would pull in `createTRPCReact` and React hooks into a non-React module. The risk is that if `GameCanvas` is ever rendered server-side, the mutations would not be available — but `GameCanvas` already has `"use client"` and is loaded via `next/dynamic` with `ssr: false`, so this is not a concern.

2. **Tree-shaking with tRPC adapter extension**: `GameTrpcAdapter` is a TypeScript interface; adding methods to it produces zero JavaScript at runtime. The concrete adapter implementation (the `useMemo` in `GameCanvas`) is entirely inside the `"use client"` component. As long as `MapEditor` does not import from `~/trpc/*` directly, tree-shaking is safe.

3. **Async operations inside a DOM-based panel**: The editor's DB calls are `async`; the panel has no React state management for loading indicators. Use button `disabled` toggling + `_showStatus` / `_showError` as the synchronous UI response. Error paths must not throw unhandled promise rejections — wrap all `await` calls in `try/catch`.

4. **`mapList()` query vs mutation in React hooks**: `api.map.list` is a tRPC `query`, not a `mutation`. In the injected-callback pattern, `useMutation` is not appropriate. Instead, use `api.map.list.useQuery(undefined, { enabled: false })` + `refetch()`, exactly mirroring the `getSave` pattern in `GameCanvas` (lines 59–61, 67, 79). Similarly for `api.map.get`.

5. **`mapSave` input type (`mapData: mapDataSchema`)**: the editor's `getMapData()` returns a `MapData` object. The `mapSave` tRPC input validates against `mapDataSchema` on the server. The client passes the raw object; the server validates. No client-side pre-validation is required, but if you want early feedback, you could call `mapDataSchema.safeParse(this.getMapData())` before the network call.

6. **List staleness**: The map list shown in the editor is fetched on demand (user clicks "Refresh List"). It does not auto-refresh. This is intentional — the editor is a single-admin dev tool; stale list is an acceptable trade-off for simplicity.
