# Plan: Issue #15 — Cell-aware map editor (fix grid alignment)

## Summary & Goal

The map editor currently snaps to a 1-unit integer grid and draws 1×1×1 cubes
(`MapEditor.snapToGrid` = `Math.round(worldPos)`, `_createBlockMesh` dims=[1,1,1]).
The runtime map uses `cellSize=2` with cells centered at odd world positions
(e.g. cell (0,0) for TestMap 60×60 is at world x=-29, z=-29).
This mismatch means:

1. Placed editor blocks never align with the visual grid (which uses
   `setTerrainGrid(60, 60, 2)` → a GridHelper with divisions matching cellSize=2).
2. `loadMapData()` rebuilds entity markers but never reads `terrain[][]` to
   produce visible cell meshes, so loading the default map shows a blank editor.
3. `getMapData()` currently returns `_mapData.terrain` verbatim — it does NOT
   incorporate `_editorBlocks`, so a round-trip (place block → getMapData)
   produces data that does not include the new block.
4. `EditorWaterZone` / `EditorHiddenTerrainZone` are separate editor-side
   collections; they are never serialized to `terrain[][]`.

The fix is to make every editor operation paint into `terrain[][]` (the
authoritative grid defined by `#14`) and to render meshes using the same
coordinate helpers (`coords.ts`) the runtime uses.

---

## 1. Cell-Aware Design

### 1a. Map dimensions in the editor

The editor must know the active map's `size` and `cellSize` at all times.
`_mapData` already tracks this (initialized to `{ name: "untitled", size: { width: 30, depth: 30 }, cellSize: 2 }` by default, though currently getMapData falls back to those defaults). Going forward, store explicit fields:

```
private _mapSize: { width: number; depth: number } = { width: 30, depth: 30 };
private _cellSize: number = 2;
```

These are set from `_mapData` on `loadMapData()` and accessible to all helpers.

### 1b. Snapping: worldToCell + cellToWorld

Replace `MapEditor.snapToGrid(worldPos)` (which rounds to nearest integer) with
a cell-based snap:

```
// imports at top of MapEditor.ts:
import { cellToWorld, worldToCell, cellMeshGeometry } from "./coords";

// New method:
private _snapToCell(worldX: number, worldZ: number): { col: number; row: number } {
  const { width, depth } = this._mapSize;
  return worldToCell(worldX, worldZ, this._cellSize, width, depth);
}

private _cellCenter(col: number, row: number): { x: number; z: number } {
  const { width, depth } = this._mapSize;
  return cellToWorld(col, row, this._cellSize, width, depth);
}
```

`worldToCell` signature (from `coords.ts`):
```ts
export function worldToCell(x, z, cellSize, mapWidth, mapDepth): { col, row }
```
`cellToWorld` signature:
```ts
export function cellToWorld(col, row, cellSize, mapWidth, mapDepth): { x, z }
```

**Every mouse handler** that calls `MapEditor.snapToGrid(worldPos.x)` is updated
to call `_snapToCell(worldPos.x, worldPos.z)` and then `_cellCenter(col, row)` to
get the snapped world-center X/Z for ghost positioning and for storing.
The static `snapToGrid` can remain for backward compatibility with tests that
exercise it directly, but all internal call sites migrate to cell-based snapping.

### 1c. terrain[][] as the single source of truth

Replace the separate `_editorBlocks: EditorBlock[]`, `_editorWaterZones:
EditorWaterZone[]`, and `_hiddenTerrainZones: EditorHiddenTerrainZone[]`
collections with direct mutation of `_mapData.terrain`.

**New internal terrain grid initializer:**
```ts
private _initTerrain(): void {
  const rows = this._mapSize.depth / this._cellSize;
  const cols = this._mapSize.width / this._cellSize;
  this._mapData = {
    ...this._mapData,
    terrain: Array.from({ length: rows }, () =>
      Array.from({ length: cols }, (): TerrainCell => ({
        type: TerrainType.Grass,
        height: 0,
        navigable: true,
      }))
    ),
  };
}
```

Editing operations become:
- `placeBlock(worldX, worldZ)` → `worldToCell(...)` → mutate `terrain[row][col]`
  with the selected type and current height; create/update the cell's mesh via `_setCellMesh(col, row)`.
- Water tool → paint `{ type: TerrainType.Water, depth: _selectedWaterDepth, navigable: false }`.
- Hidden terrain → paint `{ type: TerrainType.Hidden, height: _selectedHiddenTerrainHeight, navigable: false }`.

This eliminates `_editorWaterZones` and `_hiddenTerrainZones` as editor-level
structures. The water drag ghost is retained as a visual aid; `createWaterZone`
now iterates the rect and paints each cell.

#### Retained editor-side interfaces

`EditorBlock` is **removed** as a first-class collection. All terrain data lives
in `terrain[][]`. The `_editorBlocks` array is replaced by a 2-D handle map:

```ts
private _cellHandles: Map<string, SceneHandle> = new Map();
// key = `${col},${row}`
```

`EditorWaterZone` and `EditorHiddenTerrainZone` are **removed** as editor
collections (their data lives in `terrain[][]`). The `_editorWaterZones` /
`_hiddenTerrainZones` arrays are removed.

Point entity collections (`_playerSpawn`, `_catSpawns`, `_resourceNodes`,
`_yarnPickups`) are **retained** unchanged; they store world-space x/z
coordinates snapped to cell centers. Their existing handles and placement logic
carry over (only the snapping math changes).

### 1d. Cell mesh sizing and vertical stacking

`_setCellMesh(col, row)` creates or replaces the mesh for cell `(col, row)`:

```ts
private _setCellMesh(col: number, row: number): void {
  const key = `${col},${row}`;
  const cell = this._mapData!.terrain[row]?.[col];
  if (!cell || !this.sceneManager) return;

  // Remove old mesh if any
  const old = this._cellHandles.get(key);
  if (old) this.sceneManager.removeMesh(old);

  const { x, z } = this._cellCenter(col, row);
  const { boxHeight, centerY } = cellMeshGeometry(cell.height);
  const color = EDITOR_TERRAIN_COLORS[cell.type];

  const handle = this.sceneManager.addMesh({
    geometry: "box",
    dims: [this._cellSize, boxHeight, this._cellSize], // fill the full cell footprint
    color,
  });
  this.sceneManager.updateTransform(
    handle,
    { x, y: centerY, z },
    { x: 0, y: 0, z: 0 },
    { x: 1, y: 1, z: 1 }, // dims already include the actual sizes
  );
  this._cellHandles.set(key, handle);
}
```

`cellMeshGeometry(height)` (from `coords.ts`):
- height > 0: `{ boxHeight: height, centerY: height/2 }` — elevated slab.
- height = 0: `{ boxHeight: FLOOR_THICKNESS (0.2), centerY: -0.1 }` — thin floor slab.

Stacked layers align because the same `cellMeshGeometry` rule governs both the
runtime renderer (MapManager) and the editor.

**Ghost mesh:** When a terrain tool is active and the mouse moves, the ghost is
now `dims: [cellSize, 1, cellSize]` positioned at the snapped cell center
(floating at y=0.5 so it's visible above the floor).

**Water drag ghost:** The drag rectangle ghost is sized in cell units:
`width = (maxCol - minCol + 1) * cellSize`, `depth = (maxRow - minRow + 1) * cellSize`,
centered at the midpoint of cell centers of the corner cells.

**Hidden terrain drag ghost:** Same sizing logic as water drag.

### 1e. Selection / edit / delete in cell terms

Because terrain is now in `terrain[][]`, "select" means "select a cell":

```ts
private _selectedCell: { col: number; row: number } | null = null;
```

- Click (no tool selected) → `worldToCell(...)` → set `_selectedCell`; call
  `setMeshEmissive` on `_cellHandles.get(key)`.
- `updateSelectedBlockType(type)` → mutate `terrain[row][col].type`, call
  `_setCellMesh(col, row)`.
- `updateSelectedBlockHeight(height)` → mutate `terrain[row][col].height`, call
  `_setCellMesh(col, row)`.
- `deleteSelectedBlock()` → set `terrain[row][col]` back to default Grass/0/true;
  remove the mesh; or alternatively just clear the type to the base type. Decision:
  **reset the cell to `{ type: Grass, height: 0, navigable: true }`** and remove
  the elevated mesh (the floor slab is created on first load or implicit).

Public API surface keeps the same method names (`selectBlock`, `getSelectedBlock`,
`updateSelectedBlockType`, `updateSelectedBlockHeight`, `deleteSelectedBlock`) but
their backing type changes from `EditorBlock` to an inline `{ col, row }` record
or adapts to read/write `terrain[row][col]` directly. Keep `EditorBlock` exported
type if tests reference it, or update those tests.

### 1f. Water / Hidden tools paint cells with depth

`selectTool(TerrainType.Water)` + drag → `createWaterZone(c1, r1, c2, r2)` now
works in *cell* coordinates (col/row pairs, not world units). For each cell in the
rect:
```ts
terrain[row][col] = {
  type: TerrainType.Water,
  height: 0,
  navigable: false,
  depth: this._selectedWaterDepth,
};
this._setCellMesh(col, row);
```

`selectEntityTool("hiddenTerrain")` + drag → `createHiddenTerrainZone(c1, r1, c2, r2)`:
```ts
terrain[row][col] = {
  type: TerrainType.Hidden,
  height: this._selectedHiddenTerrainHeight,
  navigable: false,
};
this._setCellMesh(col, row);
```

Note: `TerrainType.Hidden` is already in `EDITOR_TERRAIN_COLORS`
(`"#1a1a2e"`), so the mesh will render with the correct color.

### 1g. Point-entity snapping to cell centers

`placeEntity(worldX, worldZ)` replaces `MapEditor.snapToGrid` with:
```ts
const { col, row } = this._snapToCell(worldX, worldZ);
const { x, z } = this._cellCenter(col, row);
// then place entity at (x, z)
```

Entities store their world-space x/z (cell center), which is exactly what
`getMapData()` already emits for `spawnPoints`, `resourceNodes`, `yarnPickups`.
No change to serialization.

Move tool for point entities: `_updateObjectPosition` receives the snapped cell
center rather than the raw snapped integer.

## 2. getMapData / loadMapData Round-Trip Design

### getMapData()

After the refactor, `getMapData()` becomes trivially correct:

```ts
getMapData(): MapData {
  return {
    name: this._mapData?.name ?? "untitled",
    size: this._mapSize,
    cellSize: this._cellSize,
    terrain: this._mapData!.terrain.map((row) => [...row]), // shallow copy rows
    spawnPoints: [
      ...(this._playerSpawn ? [{ x: this._playerSpawn.x, z: this._playerSpawn.z, role: "player" as const }] : []),
      ...this._catSpawns.map((s) => ({ x: s.x, z: s.z, role: "cat" as const })),
    ],
    resourceNodes: this._resourceNodes.map(({ x, z, type, respawnTime }) => ({ x, z, type, respawnTime })),
    yarnPickups: this._yarnPickups.map(({ x, z, yarnAmount }) => ({ x, z, yarnAmount })),
  };
}
```

No separate block/water/hidden serialization: it all lives in `terrain[][]`
already. The round-trip is exact by construction.

### loadMapData(data: MapData)

```ts
loadMapData(data: MapData): void {
  this._clearEditorState();  // removes all _cellHandles meshes + entity meshes

  this._mapSize = { ...data.size };
  this._cellSize = data.cellSize;
  this._mapData = { ...data, terrain: data.terrain.map((row) => [...row]) };

  // Rebuild cell meshes from terrain[][]
  for (let row = 0; row < data.terrain.length; row++) {
    for (let col = 0; col < (data.terrain[row]?.length ?? 0); col++) {
      const cell = data.terrain[row]![col]!;
      // Only create a mesh for non-default cells (or always create; depends on perf)
      // Simplest correct approach: create mesh for every non-zero / non-Grass cell
      // to match what the user would see. Floor (height=0, Grass) skips to avoid
      // filling the scene with thousands of flat meshes when loading a large map.
      if (cell.height > 0 || cell.type !== TerrainType.Grass) {
        this._setCellMesh(col, row);
      }
    }
  }

  // Rebuild entity markers (unchanged logic)
  for (const sp of data.spawnPoints) {
    if (sp.role === "player") {
      const handle = this._createEntityMarkerMesh(sp.x, sp.z, ENTITY_COLORS.playerSpawn);
      this._playerSpawn = { x: sp.x, z: sp.z, handle };
    } else if (sp.role === "cat") {
      const handle = this._createEntityMarkerMesh(sp.x, sp.z, ENTITY_COLORS.catSpawn);
      this._catSpawns.push({ x: sp.x, z: sp.z, handle });
    }
  }
  for (const rn of data.resourceNodes) {
    const handle = this._createEntityMarkerMesh(rn.x, rn.z, RESOURCE_NODE_COLORS[rn.type]);
    this._resourceNodes.push({ x: rn.x, z: rn.z, type: rn.type, respawnTime: rn.respawnTime, handle });
  }
  for (const yp of data.yarnPickups) {
    const handle = this._createEntityMarkerMesh(yp.x, yp.z, ENTITY_COLORS.yarnPickup);
    this._yarnPickups.push({ x: yp.x, z: yp.z, yarnAmount: yp.yarnAmount, handle });
  }
}
```

**This makes loading the default TestMap render it correctly.** TestMap has 30×30
cells with `cellSize=2`; `_setCellMesh` will create a mesh for each non-default
cell (the water zones and elevated terrain) positioned at the correct world-space
cell centers.

`_clearEditorState()` must be updated to iterate `_cellHandles` instead of
`_editorBlocks` and `_editorWaterZones` / `_hiddenTerrainZones`:

```ts
private _clearEditorState(): void {
  for (const handle of this._cellHandles.values()) {
    if (this.sceneManager) this.sceneManager.removeMesh(handle);
  }
  this._cellHandles.clear();
  this._selectedCell = null;
  // ... entity cleanup unchanged ...
}
```

## 3. Dev-Only / Tree-Shaking Preservation

**Current mechanism (verified in `Game.ts` lines 342–351):**
```ts
if (process.env.NODE_ENV !== "production") {
  this.mapEditor = new MapEditor(canvas, ...);
}
```

`MapEditor` is imported with a static `import` at line 28 of `Game.ts`. The
tree-shaking relies on the dead-code elimination of the `if` block, which modern
bundlers (Turbopack / webpack) perform when `process.env.NODE_ENV === 'production'`
is a build-time constant.

**Preserving this:** The plan makes no changes to this import or the guard. All
changes are internal to `MapEditor.ts`. The guard remains `!== "production"`, not
a dynamic import, which is sufficient since the bundler DCEs the entire `if` body.
No new imports into production files are introduced.

The test file (`MapEditor.test.ts`) already stubs `process.env.NODE_ENV =
"development"` via `vi.stubEnv` in `beforeEach`, so the production guard behavior
remains separately tested.

## Risks & Unknowns

### R1: No-Three/DOM test seam for new mesh geometry
**Risk:** `_setCellMesh` uses `cellMeshGeometry` from `coords.ts` (a pure
function) and calls `sceneManager.addMesh({dims: [cellSize, boxHeight, cellSize]})`.
The seam is the `MockSceneMgr.addMesh` vi.fn(). Tests must assert on the `dims`
argument of `addMesh` calls rather than reading Three.js geometry. This is
feasible — existing tests already assert `call.geometry === "box"` and
`call.opacity` — but the test author must be careful to identify which `addMesh`
call corresponds to which cell when `loadMapData` triggers many simultaneous
calls. Use `mockClear()` before targeted operations.

**Mitigation:** Create small single-cell map fixtures so `addMesh` is called
exactly once for the terrain, making assertion targets unambiguous.

### R2: getEditorBlocks() API breakage
**Risk:** `getEditorBlocks()` is used extensively in existing tests and is a
public API. Removing `_editorBlocks` means this method either returns a derived
view (iterate `terrain[][]` and return non-default cells) or is removed.
Changing it may cascade through many test assertions.

**Mitigation:** Two options:
  a. Keep `getEditorBlocks()` as a terrain-scanner that returns cells that differ
     from the default (type≠Grass or height≠0). This preserves the test surface.
  b. Migrate all tests to assert on `getMapData().terrain[row][col]` instead.
Option (b) is cleaner and more honest to the new data model. Recommended, but
budget time for the test-update scope.

### R3: Default terrain state
**Risk:** Currently `getMapData()` returns `terrain: []` when no map is loaded,
and a test asserts this (`getMapData() returns default map when no data loaded`,
line ~170). After the change, a default 30×30 grid will exist. Either the test
must be updated, or the default is `terrain: []` and `_initTerrain()` is only
called on explicit `loadMapData()` / "New Map" action.

**Mitigation:** Preserve the "empty terrain on fresh editor" behavior by
initializing `terrain = []` until an explicit `loadMapData` or "New Map" call.
The `_setCellMesh` calls in `placeBlock` must handle an uninitialized terrain
by initializing it lazily (or refusing if no map loaded).

### R4: Tree-shaking with static import
**Risk:** `MapEditor.ts` is statically imported in `Game.ts`. While the
instantiation is guarded, the module itself is included in the production bundle
unless the bundler's DCE also eliminates the import statement.

**Mitigation:** This is the pre-existing risk — unchanged by this PR. The
existing test ("production mode no-op") verifies the runtime guard, but not
bundle exclusion. The bundle grep in the verification gate catches this. If the
bundle grep fails, the fix is to convert to a dynamic import in Game.ts (which is
#16's problem surface, not #15's).

### R5: TestMap visibility with 900 cells (30×30)
**Risk:** Calling `_setCellMesh` for every non-default cell in TestMap may be
slow. TestMap has water zones and elevated cells — perhaps 100–200 non-default
cells. This is acceptable.

**Mitigation:** Profile is fine; no action needed for MVP.
